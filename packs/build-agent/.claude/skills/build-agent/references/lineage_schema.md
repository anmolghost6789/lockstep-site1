# Lineage Schema

Read this before any phase that writes or reads `lineage.json`.

`lineage.json` is the **single source of truth** for source-to-target data flow across the entire run. It is platform-neutral — it describes *what* flows where, not *how* any specific platform implements it. Platform-specific concerns live in `references/pipeline_conventions/`.

## When it is written

`/plan-build` Step 6 writes the initial `lineage.json` from discovery artifacts. All entries start with `lineage_source: "planned"`.

`/generate-dml` Step 5 (reconciliation) patches entries where artifact-writer corrections changed the planned logic. Patched entries get `lineage_source: "reconciled"`.

`/revise-build` Step 5 re-patches entries for tables in the revision scope.

## File location

```
state/run_id_<ID>/plans/lineage.json
outputs/run_id_<ID>/plans/lineage.json   ← synced copy
```

## Top-level structure

```json
{
  "schema_version": "build-agent-lineage-1.0",
  "run_id": "20260504T143000Z",
  "generated_at": "ISO 8601 timestamp",
  "tables": [ ... ],
  "dependency_graph": { ... },
  "external_sources": [ ... ]
}
```

---

## `tables[]` — one entry per target table

```json
{
  "table_id": "f_rx_weekly",
  "schema": "dw",
  "table_name": "f_rx_weekly",
  "layer": "L0 | L1 | L2 | L3 | L4",
  "wave": 4,
  "load_strategy": "FULL | INCREMENTAL | SCD2 | MERGE",
  "watermark_column": "load_date",
  "grain": "one row per prescriber + product + week_ending_date",
  "raw_passthrough": false,

  "source_tables": [
    {
      "table_id": "stg_rx_transactions",
      "join_type": "INNER | LEFT | RIGHT | FULL | CROSS | UNION",
      "join_keys": ["npi"]
    }
  ],

  "external_sources": [],

  "column_lineage": [ ... ],

  "dml_file": "generated/wave_4/f_rx_weekly_dml.sql",
  "assumptions": []
}
```

### `raw_passthrough` (boolean)

Set `true` for L0 raw landing tables. When true:
- `column_lineage` must be `[]`
- `source_tables` must be `[]`
- `external_sources[]` must reference the external source this table lands
- Pipeline generation creates an ingest task (not a transform task) for this table

### `load_strategy` values

| Value | Meaning |
|---|---|
| `FULL` | Truncate and reload every run |
| `INCREMENTAL` | Process only new/changed rows using `watermark_column` |
| `SCD2` | Slowly changing dimension — expire + insert pattern |
| `MERGE` | Upsert using MERGE statement |

### `source_tables[]`

Each entry is one source contributing to this target table. For UNION/multi-source tables, include one entry per source.

`join_type` values: `INNER`, `LEFT`, `RIGHT`, `FULL`, `CROSS`, `UNION`

### `dml_file`

Forward reference path relative to `state/run_id_<ID>/`. Pattern: `generated/wave_{wave}/{table_name}_dml.sql`. Set at plan-build time — file does not yet exist when lineage is written.

---

## `column_lineage[]` — one entry per target column

```json
{
  "target_column": "hcp_sk",
  "logical_type": "surrogate_key | integer | string | decimal | boolean | timestamp | date | json | unknown",
  "lineage_type": "direct | derived | lookup | system | constant | assumption",
  "source_tables": [
    {
      "table_id": "d_hcp",
      "source_column": "hcp_sk"
    }
  ],
  "transformation": "lookup hcp_sk from d_hcp on npi; use unknown member on miss",
  "confidence": "high | medium | low",
  "lineage_source": "planned | reconciled | assumption",
  "assumptions": []
}
```

### `lineage_type` values

| Value | When to use |
|---|---|
| `direct` | Target column = source column, no transformation |
| `derived` | Computed from one or more source columns (formula, CASE, concat, etc.) |
| `lookup` | FK lookup from a dimension or reference table |
| `system` | Generated by the system at load time (current timestamp, batch ID, etc.) |
| `constant` | Hardcoded value (unknown member SK = -1, status = 'ACTIVE', etc.) |
| `assumption` | Could not be resolved from inputs; logic was assumed |

### `lineage_source` values

| Value | Set by | Meaning |
|---|---|---|
| `planned` | `/plan-build` Step 6 | Derived from `canonical_build_model.json` at planning time |
| `reconciled` | `/generate-dml` Step 5 | Patched from a artifact-writer correction in `prevalidation_dml.json` |
| `assumption` | `/plan-build` Step 6 | Could not be resolved; marked `[ASSUMPTION]` in DML |

### `source_tables[]` in column_lineage

Use an array to handle multi-source columns (unions, coalesce across sources):

```json
"source_tables": [
  { "table_id": "raw_iqvia_laad",       "source_column": "npi" },
  { "table_id": "raw_iqvia_onekey_hcp", "source_column": "npi" }
]
```

For system-generated columns (`lineage_type: "system"`) and constants (`lineage_type: "constant"`), set `"source_tables": []`.

### `logical_type` values

Use these platform-neutral types. Pipeline generation and test generation map them to platform-specific types using `effective_conventions.json`.

`surrogate_key`, `integer`, `bigint`, `string`, `decimal`, `boolean`, `timestamp`, `date`, `json`, `binary`, `unknown`

## `dependency_graph`

```json
{
  "edges": [
    {
      "from": "stg_rx_transactions",
      "to": "f_rx_weekly",
      "type": "data_flow | lookup | execution_dependency | circular_dependency_flagged"
    }
  ],
  "waves": {
    "1": ["raw_iqvia_laad", "raw_veeva_crm_calls"],
    "2": ["stg_rx_transactions", "stg_hcp_master"],
    "3": ["d_hcp", "d_product", "d_date"],
    "4": ["f_rx_weekly", "f_crm_calls"]
  }
}
```

### Edge types

| Type | Source | Meaning |
|---|---|---|
| `data_flow` | `relationships.json` | Data flows from source to target as primary input |
| `lookup` | `relationships.json` | Target table does an FK lookup from source |
| `execution_dependency` | `build_blueprint.json` only | Execution must follow this order; no data flow or FK relationship |
| `circular_dependency_flagged` | `plan-build` detection | Circular dep detected; documented, not halted |

### Waves

Keys are wave numbers (strings). Values are arrays of `table_id`. Derived from `table_index.json`.

---

## `external_sources[]`

```json
{
  "source_id": "IQVIA_LAAD",
  "source_type": "flat_file | csv | parquet | api | database | cdc_stream | sftp | s3",
  "delivery_frequency": "real_time | hourly | daily | weekly | monthly | ad_hoc",
  "lands_in": "raw_iqvia_laad"
}
```

One entry per external source system. Populated from `inputs/context/domain_context.md`. `lands_in` must match a `table_id` in `tables[]` where `raw_passthrough: true`.

## Corrections ledger (written by artifact-writer, read by reconciliation)

artifact-writer writes corrections to `state/run_id_<ID>/generated/_validation/prevalidation_dml.json` under `"dml_corrections"`. The reconciliation step in `/generate-dml` Step 5 reads this and patches `lineage.json`.

```json
{
  "dml_corrections": [
    {
      "table_id": "f_rx_weekly",
      "column": "hcp_sk",
      "correction_type": "source_column_renamed | transformation_changed | column_insufficient | column_assumption",
      "planned_source_column": "npi_code",
      "actual_source_column": "npi",
      "planned_transformation": "lookup hcp_sk from d_hcp on npi_code",
      "actual_transformation": "lookup hcp_sk from d_hcp on npi; corrected — npi_code not found in source_column_registry",
      "confidence_impact": "none | minor | major"
    }
  ]
}
```

### `correction_type` values

| Value | When to use |
|---|---|
| `source_column_renamed` | Planned column name didn't resolve; correct name used |
| `transformation_changed` | Logic modified (type cast added, null handling changed, etc.) |
| `column_insufficient` | Column stub generated; marked `[INSUFFICIENT INPUT]` |
| `column_assumption` | Logic inferred; marked `[ASSUMPTION]` |

---

## Invariants (always true for a valid lineage.json)

1. Every `table_id` in `tables[]` appears in `dependency_graph.waves` exactly once.
2. Every `table_id` referenced in `dependency_graph.edges` exists in `tables[]`.
3. Every `lands_in` value in `external_sources[]` is a `table_id` in `tables[]` with `raw_passthrough: true`.
4. Every L0 table (`layer: "L0"`) has `raw_passthrough: true` and `column_lineage: []`.
5. Every `dml_file` path uses the pattern `generated/wave_{N}/{table_name}_dml.sql` where N matches `wave` field.
6. `source_tables[]` at the column level is `[]` for `lineage_type: "system"` and `lineage_type: "constant"`.

These invariants are checked by `/evaluate-build` faithfulness checklist item 10.
