# Runtime Contract

Read this before any phase that writes inside the active run dir (`runs/run_id_<ID>/`) or to package-level `runs/_memory/`.

## Shared Python tool scripts (use instead of inline Bash)

Four Python scripts in `.claude/skills/build-agent/scripts/` replace repeated inline code patterns:

| Script | Replaces | Usage |
|---|---|---|
| `sync_outputs.py` | `cp state/… outputs/…` blocks | `python .claude/skills/build-agent/scripts/sync_outputs.py <run_id>` |
| `validate_artifacts.py` | `ls generated/X/ \| wc -l` loops | `python .claude/skills/build-agent/scripts/validate_artifacts.py <run_id> --all` |
| `patch_session.py` | inline `python -c "import json; …"` JSON patches | `python .claude/skills/build-agent/scripts/patch_session.py <run_id> key=value …` |
| `append_log.py` | manual log section writes | `python .claude/skills/build-agent/scripts/append_log.py <run_id> <phase> <start> <end> --steps …` |

All scripts use only Python stdlib — no extra packages needed. All resolve paths relative to the repo root automatically (4 levels up from `scripts/`). Run from any working directory.

## Stable runtime folders

- `inputs/` — active user-provided project inputs
- `context/` — durable cross-run context (branding / guidance / reference)
- `runs/_memory/` — durable cross-run package memory
- `runs/run_id_<ID>/` — active run workspace (state, plans, generated, evaluation, outputs)
- `outputs/` — mirror of the active run's outputs for download / handoff

Do not rename or replace these folders.

A convenience mirror of the run dir's `outputs/` is exposed at the package level under `outputs/run_id_<ID>/`. The run dir is authoritative.

## Write strategy

During active phase work, write to `runs/run_id_<ID>/` only. At the end of each phase, sync completed artifacts to `runs/run_id_<ID>/outputs/`. This eliminates mid-phase drift between working files and deliverables.

- The run dir's working area is the working copy — always current during a phase
- The run dir's `outputs/` is the deliverable copy — updated at phase boundaries
- If `outputs/` is stale, it means the phase has not yet completed — this is correct
- `inspect-build` trusts filesystem over session.json, and trusts the working copy over `outputs/` for recency

## Scratch lifecycle

`runs/run_id_<ID>/scratch/` is a temporary workspace. Each phase that uses scratch must clean it at phase completion. Do not carry scratch artifacts across phase boundaries.

## Per-run timing log (`logs.md`)

Every phase records step-level wall-clock to `runs/run_id_<ID>/logs/logs.md`. The file accumulates across phases of the same run — **append, never recreate**.

### Format

```markdown
# Run Log — run_id_<ID>

## /analyze-inputs
*Started: 2026-05-04T10:00:00Z*

| Step | Start (UTC) | End (UTC) | Duration |
|------|-------------|-----------|----------|
| Step 1: read phase handoff and evidence | 10:00:00 | 10:03:00 | 3m 00s |
| Step 2: detect template conformance | 10:03:00 | 10:05:30 | 2m 30s |
| Step 3: resolve conventions | 10:05:30 | 10:08:00 | 2m 30s |
| Step 4: build canonical model (input-analyzer sub-agent) | 10:08:00 | 10:22:00 | 14m 00s |
| Step 5: validate and sync | 10:22:00 | 10:25:00 | 3m 00s |
| **Phase total** | **10:00:00** | **10:25:00** | **25m 00s** |

## /generate-ddl
*Started: 2026-05-04T10:40:00Z*
…
```

### Rules

- **Append-only** — when starting a phase, `Read` the file if it exists, then `Write` the same content plus the new section. Never recreate or overwrite past phases.
- **Granularity:** one row per top-level numbered Step in the phase's SKILL.md. Sub-steps collapse into their parent unless sub-agent timing genuinely matters (e.g., parallel artifact-writers).
- **Delegated steps:** include sub-agent names in the description, e.g. `Step 4: build canonical model (input-analyzer sub-agent)`.
- **Phase-total row:** bolded, one per phase section, after the last step.
- **Timestamps:** Section header uses ISO 8601 UTC. Table cells use `HH:MM:SS` UTC. If a phase crosses midnight, prefix the table cell with the date.
- **Capturing time:** use `date -u +%H:%M:%S` via Bash (read-only op). Record start at step entry and end at step exit.
- **Writing the file:** always via the `Write` tool. Never use `echo`/heredoc/`printf` to write log content (per project-wide tool-discipline rule).
- **Why this exists:** gives the user clear visibility into where wall-clock is spent, makes regressions measurable, and fuels post-run optimization decisions.

## `session.json` expectations

At minimum, runs should track:
- `schema_version` — identifier for session format compatibility
- `run_id`
- `created_at`
- `updated_at`
- `status`
- `active_phase`
- `checkpoint_history`
- `input_summary`
- `analysis_summary`
- `planning_summary`
  - `lineage_generated` (boolean) — set true by /plan-build Step 7 when lineage.json is written
  - `lineage_reconciled` (boolean) — set true by /generate-dml Step 5 after reconciliation; also set by /revise-build Step 5 after lineage patch
- `generation_summary`
  - `ddl_complete` (boolean)
  - `dml_complete` (boolean)
  - `dq_complete` (boolean)
  - `pipeline_complete` (boolean) — set true by /generate-pipeline Step 6
  - `tests_data_complete` (boolean) — set true by /generate-tests Step 5 for data tests category
  - `tests_pipeline_complete` (boolean) — set true by /generate-tests Step 5 for pipeline tests category
  - `tests_complete` (boolean) — deprecated alias for `tests_data_complete`; kept for backward compatibility
- `scope_selection`
  - `ddl`, `dml`, `dq`, `tests` (boolean) — set at Step 0 of /start-build-run
  - `pipeline` (boolean) — set at Step 0 of /start-build-run
  - `pipeline_platform` ("databricks" | "snowflake" | "generic" | null) — set by /generate-pipeline Step 1
- `evaluation_summary`
- `revision_summary`
- `packaging_summary`
- `completed_tables`
- `tables_remaining`
- `active_wave`
- `artifact_inventory`
- `remediation_status`

The authoritative structural definition lives at `references/session.schema.json` (JSON Schema Draft 2020-12). When adding or removing fields in `session.json`, update the schema file and bump the version per the policy below.

## Schema versioning

`session.json` carries a `schema_version` field for format compatibility. If `/inspect-build` encounters an older format, surface a migration recommendation.

## Checkpoint history

Record a checkpoint entry whenever user approval is required. Each entry should capture:
- checkpoint name
- phase
- requested_at
- decision
- decision_notes
- scope locked by that decision

Examples:
- proceed after quality gate
- approve canonical model
- approve plans
- continue broad generation
- approve broad revision
- approve packaging with waivers

## Memory conventions

### Seed format

If memory files are empty at the start of a run, use the structured format from `templates/memory/` as the expected schema before writing the first entries. Every memory entry must include the fields defined in the seed templates.

### Status lifecycle

Memory entries support:
- `active`
- `superseded`
- `retired`

For decisions, capture:
- decision id
- title
- decision text
- rationale
- made by
- status
- supersedes (optional)
- impact

If a later decision replaces an earlier one, it must explicitly mark that relationship.

## Evidence model

Discovery and plan artifacts should distinguish:
- `explicit_evidence`
- `inferred_logic`
- `assumptions`

When possible, evidence entries should include:
- source file
- sheet or section
- table
- row or field reference
- notes

## Packaging outputs (legacy structure)

The previous `/package-build` phase has been removed. Per-run packaging artifacts are no longer assembled into `outputs/run_id_<ID>/package/`. The assumptions register and conflict-resolution data are surfaced inline by `/evaluate-build` and `/revise-build`. If a downstream consumer needs a delivery manifest, build it externally from the synced `outputs/run_id_<ID>/` tree.
