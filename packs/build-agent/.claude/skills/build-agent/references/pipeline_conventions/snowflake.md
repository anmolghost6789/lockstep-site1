# Pipeline Conventions — Snowflake Tasks

Read this when `scope_selection.pipeline_platform = "snowflake"`.

Snowflake Tasks are SQL-defined scheduling objects. Each task wraps a SQL statement (or stored procedure call). Tasks form a DAG via `AFTER` clauses. Unlike Databricks, tasks do not reference external files — they execute SQL inline or call a stored procedure. The agent generates a single `.sql` file containing all `CREATE TASK` statements in the correct creation order.

---

## Output files

| File | Contents |
|---|---|
| `generated/pipeline/pipeline_tasks.sql` | All CREATE TASK statements — primary deployment artifact |
| `generated/pipeline/pipeline_activate.sql` | RESUME statements to activate the task graph after creation |
| `generated/pipeline/pipeline_suspend.sql` | SUSPEND + DROP statements for teardown |
| `generated/pipeline/pipeline_readme.md` | Deployment instructions, role requirements, variable guide |

## Task structure

```sql
-- pipeline_tasks.sql
-- Generated by Build Agent — run_id: <run_id>
-- Platform: Snowflake Tasks
-- Lineage source: planned | reconciled
-- Generated at: <ISO timestamp>

-- ============================================================
-- Wave 1 — Raw landing ingest tasks (roots — have SCHEDULE)
-- ============================================================

CREATE OR REPLACE TASK {{database}}.{{schema_raw}}.ingest_{{source_id}}
  WAREHOUSE = {{warehouse}}
  SCHEDULE  = 'USING CRON 0 2 * * * UTC'   -- Daily at 2 AM UTC; adjust per delivery frequency
  COMMENT   = 'Ingest external source: {{source_id}} — [ASSUMPTION] implement ingest logic'
AS
  CALL {{database}}.{{schema_raw}}.sp_ingest_{{source_id}}();
  -- [ASSUMPTION] This task calls a stored procedure for ingest.
  -- Implement sp_ingest_{{source_id}} to load from the external source into this table.
  -- Source delivery: {{delivery_frequency}} | Lands in: {{table_name}}

-- ============================================================
-- Wave 2 — Staging transforms
-- ============================================================

CREATE OR REPLACE TASK {{database}}.{{schema_staging}}.task_stg_rx_transactions
  WAREHOUSE  = {{warehouse}}
  AFTER      {{database}}.{{schema_raw}}.ingest_iqvia_laad
  COMMENT    = 'Load stg_rx_transactions — load_strategy: INCREMENTAL'
AS
  -- Source DML file: generated/wave_2/stg_rx_transactions_dml.sql
  -- Inline the DML content here. The artifact-writer reads the DML file
  -- and embeds it within the TASK AS block.
  INSERT INTO {{database}}.{{schema_staging}}.stg_rx_transactions
  SELECT ... ; -- DML content inlined from dml_file
```

## Key Snowflake Tasks rules

### Root tasks must have SCHEDULE
Every task with no upstream dependencies (L0 ingest tasks, wave 1 roots) must have a `SCHEDULE` clause. Tasks with `AFTER` must NOT have `SCHEDULE`.

### Dependency wiring via AFTER
Map `lineage.dependency_graph.edges` to `AFTER` clauses:

```
lineage edge: { "from": "d_hcp", "to": "f_rx_weekly", "type": "lookup" }
  → task f_rx_weekly:  AFTER {{database}}.{{schema}}.task_d_hcp
```

If a table depends on multiple upstreams, Snowflake Tasks support only ONE predecessor per task (classic limitation on non-serverless). For multi-predecessor cases, generate an intermediate fan-in task:

```sql
-- Fan-in barrier task: waits for all Wave 3 dimensions before Wave 4 facts begin
CREATE OR REPLACE TASK {{database}}.{{schema_dw}}.barrier_wave_3_complete
  WAREHOUSE = {{warehouse}}
  AFTER     {{database}}.{{schema_dw}}.task_d_hcp,
            {{database}}.{{schema_dw}}.task_d_product,
            {{database}}.{{schema_dw}}.task_d_date
  COMMENT   = 'Wave 3 fan-in barrier — no-op task, ensures all dims complete'
AS
  SELECT 1; -- no-op barrier
```

> Note: Multi-predecessor AFTER is supported in Snowflake serverless tasks (as of 2024). Add a YAML comment noting this when generating fan-in barriers:
> `-- NOTE: Multi-predecessor AFTER requires serverless task compute or Snowflake 2024+ task graphs`

### DML embedding
Snowflake Tasks execute SQL directly — they do not reference files. The artifact-writer must read each `dml_file` and embed the SQL content inside the `TASK AS` block. Embed verbatim with no modification.

If DML file exceeds 100KB (very rare): split into a stored procedure and call it from the task instead.

### Naming convention
`task_{table_name}` for transform tasks. `ingest_{source_id}` for L0 ingest tasks. `barrier_wave_{N}_complete` for fan-in barriers.

## Variable substitution

Use `{{placeholder}}` for all environment-specific values:

| Placeholder | Purpose |
|---|---|
| `{{database}}` | Target database (e.g., `veltrex_db_prod`) |
| `{{schema_raw}}` | L0 raw schema |
| `{{schema_staging}}` | L1 staging schema |
| `{{schema_dw}}` | L2/L3 DW schema |
| `{{warehouse}}` | Snowflake warehouse name |
| `{{delivery_frequency}}` | Source system delivery cadence (for SCHEDULE docs) |

## pipeline_activate.sql

```sql
-- pipeline_activate.sql — Run AFTER pipeline_tasks.sql is deployed
-- Activates all tasks in dependency order (leaf tasks first, root tasks last)

-- Wave 4 facts first (leaves)
ALTER TASK {{database}}.{{schema_dw}}.task_f_rx_weekly RESUME;
ALTER TASK {{database}}.{{schema_dw}}.task_f_crm_calls RESUME;

-- Wave 3 dimensions
ALTER TASK {{database}}.{{schema_dw}}.task_d_hcp RESUME;
...

-- Wave 1 root tasks last (root task RESUME triggers the DAG)
ALTER TASK {{database}}.{{schema_raw}}.ingest_iqvia_laad RESUME;
```

Activation order: leaf tasks first, root tasks last. This is the reverse of creation order.

## pipeline_suspend.sql

```sql
-- pipeline_suspend.sql — Suspend all tasks before DROP or redeploy
ALTER TASK {{database}}.{{schema_raw}}.ingest_iqvia_laad SUSPEND;
...
-- After all tasks suspended, optionally drop:
-- DROP TASK IF EXISTS {{database}}.{{schema_raw}}.ingest_iqvia_laad;
```

## pipeline_readme.md required sections

```markdown
# Pipeline Deployment Guide — <run_id>

## Prerequisites
- Snowflake role with CREATE TASK privilege on target schemas
- Warehouse: replace {{warehouse}} with actual warehouse name
- Database: replace {{database}} with environment-specific DB name

## Deployment steps
1. Run pipeline_tasks.sql to create all tasks (tasks created in SUSPENDED state)
2. Run pipeline_activate.sql to resume tasks in correct order
3. Verify DAG in Snowflake UI: Monitoring > Task Graph

## Variable substitution
Document every {{placeholder}} and per-environment values.

## Multi-predecessor note
Tasks with multiple upstream dependencies use fan-in barrier tasks.
Barrier tasks are no-op SELECT 1 statements — they exist only for DAG synchronisation.

## L0 ingest tasks
These are stub tasks calling stored procedures that must be implemented.
List each with [ASSUMPTION] notice.

## Known assumptions
List all [ASSUMPTION] entries.
```

## Pipeline test output format

When generating pipeline tests for Snowflake (`tests_pipeline/pipeline_tests.sql`):

```sql
-- pipeline_tests.sql — Snowflake pipeline tests
-- Generated by Build Agent — run_id: <run_id>
-- Tests: task existence, dependency wiring, schedule presence on roots,
--        no schedule on non-root tasks, all DML tables covered

-- ============================================================
-- Test 1: All lineage tables have a corresponding task
-- Expected: row count = 0 (no missing tasks)
-- ============================================================
SELECT table_id AS missing_task
FROM (VALUES
  ('stg_rx_transactions'),
  ('d_hcp'),
  ('d_product'),
  ('f_rx_weekly')
  -- add all non-passthrough table_ids from lineage.json
) AS expected(table_id)
WHERE table_id NOT IN (
  SELECT REPLACE(name, 'TASK_', '') 
  FROM {{database}}.INFORMATION_SCHEMA.TASKS
  WHERE SCHEMA_NAME IN ('{{schema_staging}}', '{{schema_dw}}', '{{schema_raw}}')
);
-- PASS if returns 0 rows

-- ============================================================
-- Test 2: Root tasks (wave 1) have SCHEDULE defined
-- Expected: row count = 0 (all roots have schedule)
-- ============================================================
SELECT name AS root_task_missing_schedule
FROM {{database}}.INFORMATION_SCHEMA.TASKS
WHERE SCHEMA_NAME = '{{schema_raw}}'
  AND PREDECESSORS IS NULL
  AND SCHEDULE IS NULL;
-- PASS if returns 0 rows

-- ============================================================
-- Test 3: Non-root tasks do NOT have SCHEDULE
-- Expected: row count = 0
-- ============================================================
SELECT name AS non_root_has_schedule
FROM {{database}}.INFORMATION_SCHEMA.TASKS
WHERE SCHEMA_NAME IN ('{{schema_staging}}', '{{schema_dw}}')
  AND PREDECESSORS IS NOT NULL
  AND SCHEDULE IS NOT NULL;
-- PASS if returns 0 rows

-- ============================================================
-- Test 4: All tasks reference correct warehouse
-- Expected: row count = 0
-- ============================================================
SELECT name AS wrong_warehouse
FROM {{database}}.INFORMATION_SCHEMA.TASKS
WHERE SCHEMA_NAME IN ('{{schema_raw}}', '{{schema_staging}}', '{{schema_dw}}')
  AND WAREHOUSE != '{{warehouse}}';
-- PASS if returns 0 rows

-- ============================================================
-- Test 5: Incremental tables — verify watermark column exists in target DDL
-- This is a structural check on the generated DDL, not runtime data.
-- Expected: row count = 0 (all incremental tables have watermark column)
-- ============================================================
SELECT t.table_name AS incremental_table_missing_watermark
FROM {{database}}.INFORMATION_SCHEMA.TABLES t
WHERE t.TABLE_SCHEMA = '{{schema_dw}}'
  AND t.TABLE_NAME IN (
    'F_RX_WEEKLY', 'F_CRM_CALLS', 'F_SP_DISPENSE'   -- INCREMENTAL tables from lineage
  )
  AND t.TABLE_NAME NOT IN (
    SELECT TABLE_NAME
    FROM {{database}}.INFORMATION_SCHEMA.COLUMNS
    WHERE TABLE_SCHEMA = '{{schema_dw}}'
      AND COLUMN_NAME = 'LOAD_DATE'   -- watermark_column from lineage
  );
-- PASS if returns 0 rows
```
